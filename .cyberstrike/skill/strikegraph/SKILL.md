# StrikeGraph Defensive Ontology

Use this skill when CyberStrike needs to normalize, inspect, prioritize, or govern defensive cyber information across assets, vulnerabilities, detections, incidents, evidence, controls, and countermeasures.

## Operating sequence

1. Call `strikegraph_validate` before relying on graph state.
2. Call `strikegraph_query` before creating an entity or relation so canonical IDs are reused instead of duplicated.
3. Normalize raw findings into graph entities. Keep collector-specific raw output in `Evidence`; keep semantic state in typed entities.
4. For changes, call `strikegraph_mutate` with `commit=false` first.
5. Review the returned validation result and graph diff conceptually.
6. Repeat the same mutation with `commit=true` only when valid.
7. Re-run `strikegraph_validate` after committed changes.
8. Use `strikegraph_prioritize` to rank `Exposure` entities for remediation and investigation.

## Normalization rules

- A `Vulnerability` is the general weakness or CVE.
- An `Exposure` is that vulnerability on a specific `Asset` in a specific context.
- A `Detection` describes telemetry/rule coverage; it is not proof that compromise happened.
- An `Alert` is an observed signal generated by a detection.
- An `Incident` groups investigated alerts/evidence.
- A `Countermeasure` is a defensive technique or mitigation.
- `Evidence` preserves source provenance and confidence.
- `Control` represents a governance/compliance requirement.
- `Simulation` represents synthetic or lab-only scenarios.
- `Action` is governance-bound decision state, never an unrestricted execution primitive.

## Action safety invariant

Only these `Action.mode` values are allowed:

- `recommend`
- `simulate`
- `approved`

Never represent an unapproved disruptive real-world operation as an executable action. Use `recommend` for proposed defensive changes, `simulate` for cyber-range/digital-twin execution, and `approved` only to record an externally authorized action.

## Exposure prioritization

The prioritizer combines known exploitation/KEV, internet exposure, exploitability, asset criticality, privilege impact, detection coverage, and mitigation state. Treat the score as triage support. Analysts should consider business context and evidence quality before remediation decisions.

## Canonical ingestion pattern

```text
collector result
  -> Evidence
  -> Vulnerability / Asset / Detection / Control normalization
  -> Exposure relationship context
  -> validation
  -> prioritization
  -> recommended Countermeasure / Action
  -> verification Evidence
```

Prefer explicit provenance links. Never discard the original evidence when deduplicating semantic entities.
